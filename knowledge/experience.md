# 經驗紀錄

## 2026-11-26：以一輪完整遊戲建立計分與結算

- **做法**：每次開始遊戲時複製並洗牌該模式的題目清單，逐題更新「第幾題／總題數」與得分，答對加一分；看答案可以繼續遊戲，但不會加分。最後一題後顯示成績，提供重新挑戰；開始任何模式時重置回合控制項。
- **原因**：讓玩家知道遊戲何時結束，並讓答題結果有明確回饋。複製清單後再洗牌，避免更動原始題庫順序。
- **適用範圍**：無伺服器、題目預先放在 JavaScript 陣列的單頁問答遊戲；若要跨重新整理保存紀錄、多人排名或計時賽，需另加持久化或後端設計。
- **檢查重點**：逐一遊玩每個模式；確認答對計分、揭曉答案不計分、末題結算、重玩及結算後切換其他模式都正常。

- **額外發現**：開始功能測試前先執行 `node --check`，可快速抓出字串引號等解析錯誤；本專案曾有一則提示因英文撇號未跳脫導致整支腳本無法載入。
- **適用範圍**：不使用建置工具的原生 JavaScript 靜態網站，以及修改題庫字串或內嵌文案後的快速檢查。

## 2026-11-26：只以完整別名判定正確答案

- **做法**：先把玩家輸入與各個答案別名都轉成小寫並移除空白、連字號、底線、句點及常見標點，再比較完整字串。歌曲／團體別名仍可各自列在 `answers` 中。
- **原因**：子字串比對會把答案的一小段也當作正確，造成誤判；常見格式差異則可透過正規化處理。
- **適用範圍**：答案是短文字且能列舉可接受別名的靜態測驗。若未來接受羅馬拼音變體、錯字或語音輸入，應明確加入別名或採用有門檻與測試的相似度規則。
- **檢查重點**：完整別名可通過，忽略大小寫／空白／標點仍可通過，任意前後綴或片段不得通過。

## 2026-11-26：用官方 MV／舞蹈影片校正題目線索

- **做法**：查核官方藝人或唱片公司發布的 MV、舞蹈影片，並以官方發佈日期檢查題目年份。只保留能被來源支持的具體線索；遇到錯誤年份、別名或人數描述就直接修正。
- **本次修正**：BLACKPINK〈DDU-DU DDU-DU〉原提示把年份寫成 2020，改為 2018；望遠鏡手勢改為較具辨識度的手槍手勢。BTS〈FIRE〉移除錯誤別名 `warrior`，並改正「歌名是一種戰鬥」的提示。TWICE〈Feel Special〉MV 線索改為九位成員與金色舞台。
- **適用範圍**：以真實歌曲、藝人和作品畫面作答的音樂問答題庫；年份、團員數、歌名等可由官方發布資訊核對，畫面細節仍需回看官方影片確認。
- **參考來源**：[BLACKPINK 官方〈DDU-DU DDU-DU〉MV](https://www.youtube.com/watch?v=IHNzOHi8sJs)、[BLACKPINK 官方舞蹈練習](https://www.youtube.com/watch?v=jOJbXvjZ-cQ)、[BTS 官方〈FIRE〉編舞版 MV](https://www.youtube.com/watch?v=2cTZTqBU1Rc)、[JYP 官方〈Feel Special〉MV](https://www.youtube.com/watch?v=3ymwOvzhwHs)、[TIME 對〈Feel Special〉MV 場景的描述](https://time.com/5696384/twice-interview-feel-special/)。
- **檢查重點**：引用官方影片確認作品與日期；視覺描述須能在 MV 中直接找到，避免把推測寫成線索。

## 2026-11-26：把難度標示放進題目資料並顯示給玩家

- **做法**：每道題各自標記 `easy`、`medium` 或 `hard`，在讀題時映射成繁體中文標籤顯示；新增題目時一併填難度與可接受答案別名。本輪在 Emoji、舞蹈及 MV 模式各加一題：BTS〈Dynamite〉、TWICE〈TT〉、NewJeans〈Ditto〉。
- **原因**：首頁卡片上的難度只描述模式，不能告訴玩家眼前題目的挑戰程度；題目 metadata 可讓線索和難度維持在同一筆資料中。
- **適用範圍**：靜態題庫、由前端直接渲染題目的小型遊戲。若之後想按答題正確率自動調整難度，需記錄玩家表現並另訂調整規則。
- **參考來源**：[HYBE 官方〈Dynamite〉MV](https://www.youtube.com/watch?v=gdZLi9oWNZg)、[JYP 官方 TWICE〈TT〉舞蹈練習](https://www.youtube.com/watch?v=9uypQGzzhns)、[HYBE 官方 NewJeans〈Ditto〉MV Side A](https://www.youtube.com/watch?v=pSUydWEqKwE)。
- **檢查重點**：每筆題目都有合法難度值；各模式新題可答對；每題顯示正確的中文難度；加題與洗牌後進度總題數會自動更新。

## 2026-11-26：管理對話視窗的鍵盤焦點

- **做法**：開啟題目時記住原焦點；答對或揭曉答案後把焦點移到「下一題」；Tab／Shift+Tab 在對話視窗的可用控制項間循環；關閉時把焦點還給開啟遊戲的模式按鈕。為互動控制項加上可見焦點外框。
- **原因**：讓鍵盤使用者能在開啟遊戲後留在目前流程，並在關閉時回到原入口。
- **適用範圍**：單頁網站中的非原生 HTML 對話視窗；新增或隱藏控制項時，需重新檢查焦點循環清單是否涵蓋可見項目。
- **檢查重點**：從模式按鈕開啟後使用 Tab 遍歷控制項；確認答題／揭曉後焦點落在可繼續的按鈕；Escape、關閉鈕與背景點擊都能還原原焦點。

## 2026-11-26：優先改善窄螢幕遊戲視窗

- **做法**：小於 480px 時把答案欄與送出按鈕改為直向排列，輸入文字使用 16px，互動按鈕至少 44px 高；對話視窗限制最大高度並允許內部捲動。
- **原因**：窄螢幕橫排輸入欄容易太窄，小控制項也較難觸碰；長內容需能在固定視窗內捲動。
- **適用範圍**：窄螢幕的表單對話視窗；若調整題面文字長度或加更多按鈕，需再檢查垂直空間及觸控排列。
- **檢查重點**：確認 480px 以下的斷點、輸入欄直向排列與至少 44px 控制項高度；確認長視窗內容可捲動，桌面版仍保留原先的橫向表單。

## 2026-11-26：使用 Fisher–Yates 洗牌題目

- **做法**：先複製題目陣列，再從尾端開始，每個位置都和包含自己在內的隨機位置交換。
- **原因**：`sort(() => Math.random() - 0.5)` 不符合排序器一致性要求，會導致偏斜且不可靠的排序結果；逐步隨機交換更清楚地表達洗牌目的，也保留原題庫。
- **適用範圍**：需將有限清單打亂順序的前端遊戲。若要求可重現結果或可稽核的抽獎，另需可注入的種子亂數或合適的隨機來源。
- **檢查重點**：每輪題目數量與題庫一致、每題恰好出現一次，且洗牌前後的原題庫順序不變。

## 2026-11-26：以平台功能處理第三方音樂影片

- **評估結果**：本專案先維持文字線索，不下載、剪輯或自行複製 MV／舞蹈影片影格。若產品後續需要預覽，優先使用影片平台明確提供的嵌入播放器，並逐支確認影片仍允許嵌入。
- **原因**：平台的官方文件提供嵌入方式，但亦要求遵守播放器政策；僅因影片可公開觀看，不代表可自行重製或下載。嵌入會載入第三方內容，因此應依網站受眾與隱私需求另外確認設定。
- **適用範圍**：以第三方音樂影片補充靜態網站線索的情境。自製或採授權素材仍需保存授權來源、作者與適用條款。
- **參考來源**：[YouTube 官方嵌入說明與播放器政策](https://support.google.com/youtube/answer/171780?hl=en)、[YouTube 使用條款](https://www.youtube.com/t/terms)、[Creative Commons CC BY 4.0 授權要求](https://creativecommons.org/licenses/by/4.0/deed.en)。
- **檢查重點**：確認素材來源、明確授權、平台嵌入設定、必要的署名，以及第三方載入對隱私與載入速度的影響。YouTube 說明也指出，兒童導向網站需遵守相應的自我標示要求；在確定網站受眾前不新增嵌入播放器。

- **做法**：把無相依套件的核心互動檢查放在 `.github/tests/`，以 Node.js 內建 `node:test` 驅動模擬 DOM；Pages 部署 job 必須等語法檢查與回歸檢查通過才執行。
- **覆蓋範圍**：三種模式回合、正確作答得分、揭曉答案不計分、結算與重玩、答案正規化及片段拒絕、題目難度／別名資料、鍵盤焦點循環與關閉後還原。
- **適用範圍**：純前端、無套件建置流程的靜態網站，可用 Node.js 內建測試工具維持輕量 CI。模擬 DOM 不能取代真實瀏覽器的跨裝置視覺檢查。
- **檢查結果**：`node --check script.js` 通過；`node --test .github/tests/game.test.js` 4 項通過。

### Pages artifact job 邊界

本次回歸檢查成功，但 Pages 部署 action 在同一 deploy job 找不到上一步才上傳的 artifact。將 Pages 設定與 artifact 上傳移到已完成檢查的 `verify` job，再由 `needs: verify` 的 `deploy` job 取用；部署 job 明列 `actions: read`、`pages: write`、`id-token: write` 所需權限。之後修改 artifact 產生與部署工作流程時，應依賴 job 間明確的 `needs`，並檢查 artifact 對部署 action 可見。

- **正式發布驗證**：修正 artifact job 邊界後，GitHub Actions 的 `verify` 與 `deploy` 皆成功；正式頁面 HTTP 200，遠端 JavaScript 已含新增題目。純前端專案可用 workflow 狀態與站點回應做最小端到端驗證。
- **洗牌回歸檢查**：CI 對三種模式各執行 100 輪，確認每輪每題恰好一次，且題庫原始順序保持不變。

## 2026-11-26：避免同模式題目共用藝人答案

- **發現**：新增第二首 NewJeans MV 題後，兩道題都把 `newjeans` 列作可接受答案；輸入團名會同時被視為兩首不同歌曲的正確答案。
- **做法**：當同一模式含有同藝人的多首歌時，這些題目只保留各自歌曲名稱／明確別名；CI 將每個模式的正規化答案設為唯一。
- **適用範圍**：提供多答案別名的單題測驗，尤其是同一位藝人或系列名稱可對應多題時。跨模式可以重複答案，因為每輪只從一種模式出題。
- **檢查重點**：對每個模式建立正規化答案索引，確認沒有別名同時指向兩道題；完整歌名仍能答對。
- **介面文案**：當為避免同模式多題撞答案而移除藝人別名時，輸入欄標籤與 placeholder 應明確要求歌名，且與題庫實際接受的答案一致。
- **動態提示**：提示按鈕只在操作後才更新的文字，應放入 `aria-live="polite"` 區域，讓螢幕閱讀器播報新內容；適用於測驗提示、驗證訊息及其他不移動焦點的狀態更新。

### 2026-11-26：歌名首字母提示

第二階段提示應從主要歌名答案別名取第一個字元，而非從供玩家閱讀的「藝人 — 歌名」顯示字串取字元；否則可能洩漏藝人首字母而非題目要猜的歌名。讓 `answers[0]` 固定為主要歌名別名，並以小型互動回歸測試驗證提示內容。適用於題庫答案含多個別名、介面展示又包含藝人名稱的猜歌或問答遊戲；新增題目時維持第一別名為歌名。
